# ADR-003 — Explicit canonical mapping with per-item pricing failures

**Status:** accepted
**Date:** 2026-10-12

## Context

The inputs describe the same order, but mobile timestamps are seconds, mobile identifiers lack PROD-, and B2B identifiers include SKU-. B2B bytes declare windows-1257; decoding them as UTF-8 damages Latvian names. XML has another hazard: automatic numeric conversion loses leading zeros in postal codes, and one LineItem becomes an object instead of an array. Prices come from an authenticated service that can return 404, 401 or 500. Payment fields appear under web customer.payment, mobile pm/pan/pexp, and B2B BuyerParty.PaymentDetails.

## Decision

Each translator constructs the canonical object explicitly, including its address. It never spreads source objects. Unknown XML elements are ignored, so neither payment details nor newly added source fields travel accidentally. Source product names and quantities are retained; pricing supplies unitPrice, item currency and taxRate.

decodeB2BXmlBytes uses TextDecoder("windows-1257"). XMLParser retains text values as strings; translateB2B normalizes singleton LineItem objects to arrays and converts only quantity to a number. Dates use toISOString, including the mobile seconds-to-milliseconds conversion. Identifier transformations are prefix operations rather than a catalog lookup table, so new product IDs need no code change.

enrichFromPricing sends X-API-Key, limits requests to five seconds, and validates successful responses. toDecimalAmount formats the API number once with toFixed(2), turning 4.5 into "4.50". Invalid bodies, network failures and non-success responses become PRICING_API_ERROR warnings; 404 becomes UNKNOWN_PRODUCT. enrichItems omits only failed lines, preserves successful line order, and returns null when none remain. Warnings contain identifiers and status information, not source payloads or response bodies. Unknown currency codes pass through as strings because the schema permits that; unknown statuses/order types and malformed addresses are rejected instead of given invented meanings.

## Alternatives considered

Failing an entire order for one missing product would discard independently usable lines. Falling back to source list prices or zero would conceal an outage. Integer cents would help arithmetic but violate this contract. Deleting known payment keys would miss future fields; explicit mapping avoids that. Caching would reduce calls but could serve stale prices, so every translation requests current values. Automatic XML text conversion is convenient but inappropriate for postal identifiers.

## Consequences

TypeScript checking, 17 unchanged public tests and six additional edge-case tests passed against Docker mock-pricing. Tests cover runtime prices, CP1257, singleton XML, unknown elements, 404/401/500, connection failure and malformed pricing responses. This implementation and ADR were prepared with AI assistance; no personal student experience is claimed.

Consumers must inspect warnings because valid output can contain fewer lines. There is no retry or cache, and concurrent per-line requests have no concurrency limit; large orders need throttling. Arbitrary malformed source files can still throw: the non-throwing behavior covers enrichment failures. A fourth source needs a new adapter; a required canonical field needs all adapters updated. For a longer-lived model, versioned contracts and runtime validation at the boundary would make changes explicit. Decimal formatting does not provide exact decimal arithmetic.

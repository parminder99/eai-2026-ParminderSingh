# ADR-004 — Separate permanent failures from retryable failures and replay to the origin

**Status:** accepted
**Date:** 2026-10-12

## Context

The semester repository contained an older PA5 scaffold. The current course brief and portal additionally require consumer-declared error channels, malformed-message classification and DLQ replay. The updated scaffold was copied without altering its public tests. Its topology retries only the failing queue through orders.return.exchange, rather than repeating healthy consumers through the fanout.

The older helper counted both rejected and expired x-death entries: one TTL retry produces both, so it reached the three-attempt threshold early. The current shared helper counts rejected entries only. A configured zero failure rate must also remain zero. Verification showed a duplicate after notification-service restart left exactly one notification.log line; original order retrieval preserved the canonical body unchanged.

## Decision

order-service publishes a persistent, unchanged canonical order with a fresh UUID in headers.correlationId. That location follows the supplied contract without adding a forbidden canonical field. POST /orders returns 201 after publisher confirmation; its Map supports correlation-keyed lookup.

Each consumer declares the durable fanout exchanges orders.dlq.exchange and orders.invalid.exchange, their durable queues, and identical bindings before consuming. JSON.parse runs inside try. A SyntaxError or InvalidMessage (missing identifiers or required notification fields) is permanent: original bytes and headers go directly to orders.invalid, with no retry. Simulated failures and operational errors take the supplied bounded retry path. DLQ publications are persistent and add originQueue. getRetryCount counts rejected deliveries, so MAX_RETRIES=3 gives three attempts separated by two one-second delays. The latest provided retry/DLQ policy is retained.

POST /dlq/replay reads a snapshot-sized batch from orders.dlq. It publishes each original body to orders.return.exchange with originQueue as the routing key; withoutRetryHistory removes dead-letter history but retains correlation. Each DLQ delivery is acknowledged only after publisher confirmation. Unknown origins fail rather than route arbitrarily. Concurrent replay requests receive 409; a batch boundary prevents a still-failing consumer creating an endless HTTP replay loop. Invalid messages have no replay route because their producer must be fixed.

Notification processing checks identifiers stored in processed-ids.json. First processing appends one notification.log line, updates the Set, and writes the index through a temporary file and rename. Startup recovers identifiers from the log as well, closing the normal restart gap between append and index update. Duplicates are acknowledged without another log line or result event. Success results are published before acknowledgment; no atomic transaction with disk is claimed.

Docker images expose installed dependencies through /node_modules so /shared resolves amqplib without a host install. Runtime TypeScript aliases no longer point at declaration files; those aliases made tsx try executing a .d.ts file. Typechecks use the same corrected configuration.

## Alternatives considered

An in-memory Set loses identifiers on restart. A database unique constraint coordinates replicas better, but adds a database outside this exercise. Requeue=true avoids the delay and can spin indefinitely. Combining malformed messages with exhausted retries would invite futile replay of unparseable input. Fanout replay would repeat healthy inventory and notification work, so origin-specific routing is retained. Longer delays would tolerate a thirty-second outage; the exercise keeps its short window and requires explicit replay after repair.

## Consequences

Consumers separate permanent diagnosis from temporary recovery. Correlation survives retry and replay without altering the canonical model. Implementation, testing and this ADR were prepared with AI assistance; no personal student authorship is claimed.

Order lookup is lost on restart. Dedup files grow and cannot safely coordinate two notification replicas. File writes and result publications are not atomic, and the provided consumer publish/ack sequence has no publisher confirm; crashes can still lose result or error events. Three attempts cannot absorb a long provider outage, so an operator must repair and replay. A partial replay failure can already have forwarded some messages. Production needs durable order storage, a transactional outbox, coordinated deduplication, audited replay and downstream failure reporting.

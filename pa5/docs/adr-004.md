# ADR-004 — Header correlation and bounded retries with persistent notification deduplication

**Status:** accepted
**Date:** 2026-10-12

## Context

Each consumer needs an independent result and failure path. The canonical order forbids extra properties, so putting correlationId into its body would invalidate it. The actual topology returns each TTL retry to its own consumer queue through orders.return.exchange; the introductory comments describing fanout redelivery are outdated.

Two concrete scaffold bugs affected the intended behavior: Number(PAYMENT_FAIL_RATE) || 20 converted a configured zero into 20%, and getRetryCount summed both rejected and expired x-death entries. One retry cycle records both events, so that sum reaches the three-attempt threshold after only two deliveries. Locally, the public DLQ and correlation tests passed after correcting these. A separate duplicate test after notification-service restart left exactly one matching notification.log line.

## Decision

order-service validates the canonical shape, republishes the body unchanged to orders.exchange, and carries a fresh UUID only in headers.correlationId. This location follows the consumer and test contract; the native AMQP correlationId property would require coordinated changes. HTTP 201 follows broker publisher confirmation. The in-memory lookup is keyed by the UUID, preserving the original orderId.

Payment and inventory publish a success event with the same header. The reference retry/DLQ catch block is unchanged and is copied to the other consumers. getRetryCount counts rejected entries only, excluding TTL expiry. MAX_RETRIES=3 therefore permits three processing attempts, separated by two one-second waits. A zero failure percentage remains zero through nullish-default parsing. Malformed deliveries are parsed within the protected block so they follow the bounded failure path.

Notification processing checks the persisted identifier set before touching the log. The first successful attempt appends one JSON line, adds the identifier, and persists processed-ids.json through a temporary file and rename. Startup also recovers identifiers from notification.log, closing the ordinary process-restart gap between appending the log and updating the index. Duplicates are acknowledged and logged as duplicate skipped, without another notification or result event. Network result publication precedes acknowledgment; no stronger transaction guarantee is claimed.

Docker images expose their installed dependencies through /node_modules so the read-only /shared helper can resolve amqplib on a fresh checkout. The scaffold's TypeScript alias to an amqplib declaration file was removed: tsx interpreted it as a runtime module and failed. Both the corrected configuration and the unchanged business contracts pass typechecking.

## Alternatives considered

An in-memory Set alone loses identifiers on restart and repeats notifications after redelivery. A database unique constraint would coordinate multiple replicas and scale better than rewriting a JSON file, but adds a database beyond this exercise. Requeue=true skips TTL backoff and can spin indefinitely; the provided dead-letter path is bounded. Returning retries through the fanout exchange would make healthy services process another consumer's failures, so the supplied direct return topology stays unchanged. A longer retry window could survive a thirty-second provider outage; this exercise keeps its short window and reports failure through the DLQ instead.

## Consequences

All eight public tests and four service typechecks passed. Extra checks verified restart deduplication, unchanged order retrieval, invalid-body rejection, and dependency resolution without shared/node_modules. This code and ADR were prepared with AI assistance; no personal student authorship or debugging experience is claimed.

Order lookup disappears on restart. Dedup files grow and are unsuitable for multiple notification replicas. The file writes and result event are not atomic; a crash or disk failure can still lose a result, and the unchanged reference DLQ publication has no publisher confirm. Three attempts cannot absorb a long outage: an operator must inspect and replay the DLQ. Missing correlation headers break tracing and enter the failure path. Production needs a durable order store, a transactional outbox, coordinated deduplication and explicit failure reporting to downstream workflows.

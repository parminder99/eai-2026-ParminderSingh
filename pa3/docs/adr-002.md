# ADR-002 — Correlated aggregation with an idle timeout

**Status:** accepted
**Date:** 2026-10-06

## Context

Independent worker queues can deliver results out of order, twice, or never. The main design choice was how to make completion and timeout compete without producing two answers. Correlation itself was prescribed: every split message retains the order identifier, original item index, and original item count.

## Decision

The router copies orderId into correlationId, preserves each item unchanged, and publishes persistent messages to the three durable queues. Publisher confirms precede acknowledgment of the incoming order. Unsupported types go to a durable orders.unroutable quarantine queue with a log entry; routing them to a physical worker would falsely report fulfillment. Empty orders receive an empty completion directly.

The aggregator stores one dictionary per orderId, with results keyed by itemIndex. The first result wins; duplicates do not increase the count. Valid results, including duplicates, reset a monotonic last-activity timestamp. A shared lock protects both result callbacks and the once-per-second timeout sweep. Under that lock, completion or timeout freezes one pending snapshot; publication happens outside the lock through a separate connection. Failed publications remain pending for retry. A terminal identifier set prevents late or repeated results from reopening an order.

The test timeout remains five seconds from the most recent valid result. For production, start with 30 seconds only as a provisional value, then measure the high-percentile gap between successive results under peak load and worker recovery. Tune above normal gaps with operational margin. Total order duration is unsuitable: 50 sequential physical items can remain healthy for much longer than five seconds.

Partial messages retain all distinct received results and list every missing index in ascending order. This lets consumers identify retry candidates rather than guess from an incomplete count. Malformed results and inconsistent counts are logged and acknowledged to prevent poison-message loops.

## Alternatives considered

A fixed deadline would incorrectly terminate large orders whose workers are still progressing. Counting deliveries would confuse redelivery with a new item. Publishing while holding the lock would block unrelated orders on broker latency. Redis or a database would preserve aggregation and terminal state across restarts, but adds deployment and transaction work beyond this scaffold; memory is adequate for this single-process exercise.

## Consequences

Orders stay isolated, duplicate results cannot inflate totals, and one terminal snapshot wins the timeout/completion race. Local behavioral checks cover large and interleaved orders, duplicates, idle reset, timeout, late arrivals, and publication retry; All 10 supplied public tests subsequently passed against the rebuilt Docker Compose stack on October 6, 2026. This implementation and ADR were prepared with AI assistance, and do not claim personal testing or experiences by the student.

In-memory state is lost on restart, including already acknowledged results; terminal identifiers also grow for the process lifetime. Publisher-confirm ambiguity can still produce duplicate completions after a network failure, so this is not crash-safe exactly-once delivery. Production needs persistent aggregation, an outbox, and consumer deduplication. An order with no worker results cannot start the aggregator's timer because the scaffold supplies no order-start event. An entirely unsupported order likewise remains quarantined without a completion. Addressing these requires an explicit start/manifest protocol. Quarantine monitoring and durable recovery are accepted follow-up costs.

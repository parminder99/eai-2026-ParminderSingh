# ADR-008: Three deduplication boundaries

Status: accepted

## Context
Network retries, broker redelivery and submitting the same business order under a fresh key are distinct events.

## Decision
Use raw-byte Idempotency-Key records at intake; correlation records plus source:orderId ownership at the saga; and processed outcome correlation IDs at the notifier. Use authorize/reserve/refund/release:businessKey on provider calls.

## Alternatives considered
Using only the HTTP key permits a fresh key to charge twice. Using only message IDs misses business duplicates. Global exactly-once transport is unavailable.

## Consequences
Changing bytes under an existing key returns conflict. A new purchase after a declined order needs a new orderId. Notices remain at least once across the send/save crash gap because the notification mock offers no deduplication contract.

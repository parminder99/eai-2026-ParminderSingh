# ADR-006 — Durable workflow state with per-call activities and bounded retries

**Status:** accepted
**Date:** 2026-10-22

## Context

The PA6 crash experiment killed the orchestrator after payment and inventory completed, while shipping was delayed. Its idempotency file retained in_progress with those two trace entries; after restart, the same key returned 409 idempotency_conflict. That guard prevents blindly charging twice, but it cannot finish the interrupted business operation. PA7 moves continuation into Temporal history instead of another recovery flag in a JSON file.

A refused payment and a missing service require different retry decisions. Repeating a 422 payment_declined will not repair the business refusal. Retrying a temporary transport or 5xx failure can succeed. A worker death introduces a third problem: the external service may have acted even when its activity completion was never recorded.

The separate PA7 crash run completed with HTTP 200 after restarting the worker: payment and inventory were called once, shipping twice, and notification once. All 13 public tests passed, including the automated worker-kill test. Extra checks also covered notification refusal, failed release followed by refund, failed-result replay and an exact 0.70 payment total.

## Decision

The six exported activities use post with environment-supplied URLs and the prescribed bodies. Every 4xx becomes ApplicationFailure.nonRetryable with the mock's code. Other non-success responses become retryable ApplicationFailure; transport errors remain ordinary errors. The activity's cancellation signal is passed to fetch. Temporal, rather than an activity-side timeout loop, owns the attempt budget.

checkout is deterministic workflow code. It imports activities only as types and invokes their proxies; it has no filesystem, environment or HTTP access. The proxy uses startToCloseTimeout 2500 ms, maximumAttempts 3, initialInterval 200 ms and backoffCoefficient 2. Trace entries cover all attempts using workflow-safe Date timestamps, one entry per step.

amountFor adds BigInt whole cents and formats a two-digit amount without floating-point multiplication. The four calls are awaited sequentially. Completed payment and inventory flags determine reverse compensation: releaseInventory followed by refundPayment. A failed release still permits the refund attempt. failureCode unwraps ActivityFailure: TimeoutFailure becomes timeout, while ApplicationFailure.type preserves the service code. Every outcome returns CheckoutResult; compensation failure overrides the original error as failed/compensation_failed. There is no invented shipping cancellation.

The given API and worker startup remain unchanged. Workflow IDs and memo hashes implement request idempotency; file stores mirror results for audit. They do not drive workflow continuation.

## Alternatives considered

A PA6 startup recovery job would need durable per-step state, retries, timers, leases and reconciliation for calls whose result was lost. This is possible, but becomes another workflow engine to operate and test. Putting the entire saga in one activity hides progress from Temporal and would repeat earlier side effects after a failure. Retrying every 4xx wastes attempts and delays a refusal the caller should see immediately. A BPMN engine could suit analyst-owned processes; this assignment's typed code and HTTP activities fit workflow-as-code with fewer translation layers.

## Consequences

Durable history makes continuation independent of one worker process. It does not make HTTP effects exactly once: a worker can die after a provider accepts a call but before completion is recorded. If that call authorizes payment, the provider needs its own durable idempotency key; the supplied mock API offers no such guarantee.

Temporal adds a server, persistent history storage, monitoring and workflow-version compatibility. Changing branches or activity order for a running workflow needs versioning or a compatible deployment. Files remain an audit mirror and may lag engine state. Shipping can succeed after the caller times out and cannot be undone here. Implementation, testing and this ADR are AI-assisted; no personal student authorship is claimed.

## What the engine took over

- Continuation: PA6 runSaga kept paid/reserved flags only in the live process. Temporal rebuilds the same workflow state from recorded activity completions after a worker restart.
- Timeout scheduling: PA6 callDownstream created an AbortSignal for every HTTP call. Temporal enforces startToCloseTimeout and delivers TimeoutFailure after the retry budget is exhausted.
- Retry scheduling: PA6 had no durable activity retry scheduler. proxyActivities now declares a three-attempt policy whose timer state lives in Temporal.
- In-flight identity and result replay: PA6 saveRecord and the checkout handler coordinated JSON records. The given PA7 API uses workflowId, memo payload hash and the workflow's durable result instead.

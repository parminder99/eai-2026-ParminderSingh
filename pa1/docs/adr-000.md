# ADR-000 — Legacy file ingestion

**Status:** accepted

**Date:** 2026-09-14

## Context

The PA1 input contains two files with different formats and encodings. The order file is a fixed-width text file encoded as CP1257 (`windows-1257`), while the customer master is UTF-8 and uses semicolons as separators.

Reading the order file as UTF-8 would decode Latvian customer names incorrectly. For example, names containing characters such as Bērziņš and Šmite would not be preserved correctly. The fixed-width layout also means that splitting a line by whitespace would be unsafe because the customer name itself contains spaces.

The order file has exactly 77 characters for a valid record. The fields are stored at fixed positions, with trailing spaces used as padding. There is also a malformed record in the input that is shorter than 77 characters. The amount field uses a comma as the decimal separator and can contain negative values, so treating it as a JavaScript number could lose formatting such as the trailing zero in `45,20`.

## Decision

The `ingest` function reads the customer file as UTF-8 and parses its semicolon-separated fields. The order file is first read as bytes and decoded using the standard Node.js `TextDecoder` with `windows-1257`.

Each order line is checked before parsing. A line is accepted only when it has exactly 77 characters. The fields are extracted using fixed column positions defined in `ORDER_LAYOUT`, then trailing padding is removed with `trim()`.

The order date is converted from `DD.MM.YYYY` to `YYYY-MM-DD` by rearranging the date parts rather than using JavaScript's `Date` parser. The amount is kept as a string and only the comma decimal separator is changed to a dot, so values such as `45,20` remain `"45.20"` and negative values remain negative.

Malformed records are not allowed to stop the whole ingestion. They are added to `rejected` with their line number, original raw content, and a reason. Customer IDs from accepted orders are tracked so that customers from the master file with no accepted order can be returned in `unmatchedCustomers`.

## Alternatives considered

Using UTF-8 to read the order file was rejected because the source file is encoded as CP1257 and Latvian characters can be corrupted.

Adding a package such as `iconv-lite` was rejected because the assignment requires the solution to use the Node.js standard library only. `TextDecoder` provides the required decoding without an additional dependency.

Parsing the order records with whitespace splitting or a regular expression was rejected because the format is defined by fixed character positions and customer names can contain spaces. Fixed-position slicing is clearer and matches the source format directly.

Storing the amount as a JavaScript number was rejected because the report must preserve decimal formatting. A value such as `45,20` must become the string `"45.20"` rather than a number that could later be formatted as `45`.

Throwing an error when a malformed line is found was rejected because one bad record should not prevent the valid records from being ingested. Collecting rejected records also makes the result auditable.

As a longer-term alternative, asking the upstream system to provide a well-defined JSON or another modern structured format would remove much of the legacy parsing complexity. That is not possible for this assignment because the existing file format is the required input, but it would be preferable for a system that had to be maintained for many years.

## Consequences

The implementation is now explicit about the source file's encoding, fixed-width layout, malformed records, date format, and decimal representation. Valid records can be processed even when another record is malformed, and the report explains which records were rejected.

The main cost is that the parser is tightly coupled to the 77-character legacy format. If the upstream system inserts a field in the middle of a record or changes a field width, the column positions in the implementation must be updated. A customer name longer than the allocated 32 characters would also not fit the current format correctly.

If the upstream system sends the order file as UTF-8 by mistake, decoding it as CP1257 can produce incorrect text, so the current solution assumes that the documented encoding is followed. The simple customer CSV parsing also relies on the assignment's guarantee that fields do not contain semicolons or quoted CSV content.

These limitations are acceptable for the current integration because they make the required legacy format explicit and keep the implementation small, dependency-free, and easy to test.
